# Memory Forensics with Volatility 3

Physical RAM is the most volatile and information-dense artifact in digital forensics. While disk analysis shows what was stored in the past, volatile memory captures what is running right now: active network connections, decrypted file streams, injected shellcode, unlinked processes, encryption keys, and plaintext credentials that may never touch persistent storage.

Volatility 3 is the modern standard for offline memory analysis. Rebuilt from the ground up on Python 3, it replaces the static profile system of Volatility 2 with dynamic symbol tables and modular memory layers. This writeup breaks down how memory dumps represent physical hardware, how Volatility 3 translates kernel structures, and how to use its core Windows plugins during an investigation.

---

## Physical Memory Architecture and Dump Formats

Operating systems view physical memory through hardware paging structures. On modern 64-bit x86 systems, the CPU uses 4-level paging (PML4) to translate 48-bit virtual addresses into physical page frame numbers (PFNs). Each standard memory page occupies 4096 bytes (4 KB).

When an acquisition tool dumps RAM, it reads physical memory sequentially or page by page through direct kernel handles (such as `\Device\PhysicalMemory`) or specialized acquisition drivers, streaming the raw bytes to disk.

### Common Dump Formats

* **Raw Binary (`.raw`, `.bin`, `.dd`)**: Unstructured bit-for-bit copies of physical memory. This is the cleanest and most common format for forensic analysis because it introduces zero proprietary container overhead.
* **Crash Dumps (`.dmp`)**: Generated by Windows during a bugcheck (Blue Screen of Death). These contain memory headers, processor context records, and either full RAM or kernel-only structures depending on crash dump settings.
* **Virtualization Snapshots (`.vmem`, `.vmsn`, `.sav`)**: Created by hypervisors like VMware, VirtualBox, or Hyper-V. These contain guest physical memory alongside CPU register states.
* **LiME Dumps (`.lime`)**: Generated by the Linux Memory Extractor kernel module, containing custom headers with range-based address descriptors.

### Binary Layout in Memory

Opening a raw dump in a hex editor shows continuous streams of binary allocations without filesystem boundaries:

```text
00000000  4D 5A 90 00 03 00 00 00 04 00 00 00 FF FF 00 00  MZ..............
00000010  B8 00 00 00 00 00 00 00 40 00 00 00 00 00 00 00  ........@.......
```

Here `0x4D 0x5A` (`MZ`) marks the DOS header of a Windows executable mapped in RAM. Interspersed between binaries are kernel object pools, thread stacks, network buffers, heap allocations, and cached file blocks.

## Volatility 3 Architecture and Symbol Resolution

In Volatility 2, parsing memory required matching the dump against static OS profiles (such as `Win7SP1x64` or `Win10x64_19041`). As Microsoft introduced monthly servicing updates, kernel offsets shifted constantly, causing profiles to break frequently.

Volatility 3 eliminates static profiles entirely. It uses Intermediate Symbol Format (ISF) JSON tables generated directly from Microsoft debugging symbols (PDBs).

### Core Components

1. **Memory Layers**: Abstract data access across physical files, translation layers (virtual-to-physical address translation via CR3/DTB), and compressed memory segments.
2. **Symbol Tables**: Provide field offsets, data types, and sizes for kernel structures (`_EPROCESS`, `_FILE_OBJECT`, `_CMHIVE`) matching the exact build of the target system.
3. **Plugins**: Independent modules that consume memory layers and symbol tables to extract structured forensic data.

### Setup and Verification

```bash
# Clone the repository
git clone https://github.com/volatilityfoundation/volatility3.git
cd volatility3
pip install -r requirements.txt

# Run help to verify symbol downloads
python3 vol.py -h
```

#### Kernel Mechanics

To parse an unknown dump without configuration flags:

1. **KDBG and KPCR Scanning**: Volatility searches physical memory for signatures matching the Kernel Debugger Data Block (`_KDDEBUGGER_DATA64`) or Kernel Processor Control Region (`_KPCR`).
2. **Directory Table Base (DTB)**: The DTB value (loaded into CPU register `CR3`) specifies the physical address of the page directory table for the `System` process. This is the root anchor for all subsequent virtual address lookups.
3. **PDB GUID Retrieval**: Volatility reads the debug directory of the mapped `ntoskrnl.exe` image, extracts the PDB name (`ntkrnlmp.pdb`) and its unique GUID (`3844DBB9...`), and automatically downloads the matching symbol file from Microsoft Symbol Servers.

#### Kernel Mechanics

In the Windows executive, every process is represented by an `_EPROCESS` structure allocated in kernel non-paged pool memory. Within `_EPROCESS`, the member `ActiveProcessLinks` is a circular doubly-linked list (`LIST_ENTRY` containing `Flink` and `Blink` pointers) rooted at the kernel variable `PsActiveProcessHead`.

`windows.pslist` begins at `PsActiveProcessHead` and traverses `Flink` pointers to visit each active `_EPROCESS`.

**Forensic Blind Spot**: Because `pslist` relies entirely on the integrity of this doubly-linked list, rootkits that employ Direct Kernel Object Manipulation (DKOM) can unlink a malicious process from `ActiveProcessLinks`. The unlinked process continues executing normally because the Windows thread scheduler schedules threads from the `_KTHREAD` dispatcher list, not the process list. To detect unlinked processes, investigators use `windows.psscan`, which scans memory for `_EPROCESS` pool tag signatures rather than relying on list traversal.

#### Kernel Mechanics

Each `_EPROCESS` structure stores its own ID in `UniqueProcessId` and the spawning parent ID in `InheritedFromUniqueProcessId`. The plugin maps these fields into a tree graph.

This layout immediately reveals execution context:
* `services.exe` spawning multiple `svchost.exe` worker instances is normal. An instance of `svchost.exe` spawned directly by `explorer.exe` or `cmd.exe` would be an immediate indicator of compromise.
* User applications (`chrome.exe`, `WinRAR.exe`, `DumpIt.exe`) correctly appear under `explorer.exe` (PID 1944).

### windows.cmdline: Runtime Process Arguments

Process executable names are truncated to 15 characters in `_EPROCESS.ImageFileName`. To see the full path and command line flags, `windows.cmdline` inspects the user-mode Process Environment Block (PEB).

```bash
vol -f MemoryDump_Lab6.raw windows.cmdline
```

```text
PID     Process         Args

880     cmd.exe         "C:\Windows\system32\cmd.exe"
2124    chrome.exe      "C:\Program Files (x86)\Google\Chrome\Application\chrome.exe"
3716    WinRAR.exe      "C:\Program Files\WinRAR\WinRAR.exe" "C:\Users\Jaffa\Desktop\pr0t3ct3d\flag.rar"
4084    DumpIt.exe      "C:\Users\Jaffa\Downloads\DumpIt.exe"
```

#### Kernel Mechanics

1. Volatility resolves `_EPROCESS.Peb`, which contains the 64-bit virtual address of the PEB in the process user-space.
2. It reads `_PEB.ProcessParameters`, pointing to `_RTL_USER_PROCESS_PARAMETERS`.
3. Inside this structure, the member `CommandLine` is stored as a `UNICODE_STRING` (Length, MaximumLength, Buffer pointer).
4. Volatility translates the virtual pointer using the process page tables and extracts the raw command line string.

This exposes the exact target file passed into WinRAR: `"C:\Users\Jaffa\Desktop\pr0t3ct3d\flag.rar"`.

### windows.filescan: Scanning Kernel File Objects

`windows.filescan` searches pool memory for active and cached `_FILE_OBJECT` structures, revealing files referenced by the system regardless of whether an open user handle currently exists.

```bash
vol -f MemoryDump_Lab6.raw windows.filescan
```

```text
Offset          Name

0x3e1ceeb0      \Windows\System32\samlib.dll
0x5ce6fb10      \Windows\System32\dui70.dll
0x5d9856d0      \Users\Jaffa\AppData\Local\Google\Chrome\User Data\Default\History
0x5fcfc4b0      \Users\Jaffa\Desktop\flag.rar
0x5fec1b40      \Users\Jaffa\AppData\Local\Microsoft\Windows\Explorer\thumbcache_256.db
```

#### Kernel Mechanics

When a file is opened on Windows, the I/O manager creates a `_FILE_OBJECT` in kernel pool memory. This object stores:
* `FileName`: A `UNICODE_STRING` storing the relative file path.
* `DeviceObject`: Pointer to the underlying storage device.
* `Vpb`: Volume Parameter Block describing the filesystem mount.
* `SectionObjectPointer`: Pointers connecting the file to Cache Manager and memory manager control areas.

Because `windows.filescan` scans memory pages for pool tags rather than traversing an active handle table, it uncovers files that were recently closed but whose structures remain resident in the kernel file system cache.

### windows.dumpfiles: In-Memory File Carving

Once a `_FILE_OBJECT` address is identified via `filescan`, `windows.dumpfiles` extracts the underlying file pages directly from volatile memory.

```bash
vol -f MemoryDump_Lab6.raw -o ./extracted windows.dumpfiles --virtaddr 0x5fcfc4b0
```

#### Kernel Mechanics

The plugin uses the `_FILE_OBJECT.SectionObjectPointer` to reach the `_CONTROL_AREA` and `_SEGMENT` structures maintained by the Memory Manager. These structures contain subunit arrays pointing directly to physical page frames that store file data in the system cache. Volatility stitches these pages together and writes the reconstructed binary to disk.

### windows.envars: Process Environment Blocks

`windows.envars` dumps all environment variables for target processes, reading configuration keys and potentially leaked credentials.

```bash
vol -f MemoryDump_Lab6.raw windows.envars --pid 4084
```

```text
PID     Process          Offset      Variable Name           Value

4084    DumpIt.exe       0x4e1dc0    ProgramFiles(x86)       C:\Program Files (x86)
4084    DumpIt.exe       0x4e1dc0    ProgramW6432            C:\Program Files
4084    DumpIt.exe       0x4e1dc0    PSModulePath            C:\Windows\system32\WindowsPowerShell\v1.0\Modules\
4084    DumpIt.exe       0x4e1dc0    RAR password            easypeasyvirus

4084    DumpIt.exe       0x4e1dc0    USERNAME                Jaffa
4084    DumpIt.exe       0x4e1dc0    USERPROFILE             C:\Users\Jaffa
```

#### Kernel Mechanics

Environment blocks are stored in the user-mode address space at `_RTL_USER_PROCESS_PARAMETERS.Environment`. This block contains a contiguous null-terminated list of wide-character strings formatted as `KEY=VALUE`, terminated by a double-null sequence.

Processes inherit environment blocks from their parent at creation time. In this artifact, the secret `RAR password=easypeasyvirus` leaked into child process environments, allowing straightforward decryption of password-protected archives.

Locating hive base offsets allows downstream plugins (`windows.registry.printkey`) to query Run keys, user accounts, and system configuration directly from RAM.

### windows.malware.malfind: VAD Tree and Injected Code Hunting

`windows.malware.malfind` detects memory injections, unpacked shellcode, and hollowed processes by scanning for executable memory regions that lack disk backing.

```bash
vol -f MemoryDump_Lab6.raw windows.malware.malfind
```

```text
PID     Process       Start VPN   End VPN     Tag     Protection               CommitCharge    PrivateMemory  File output

1944    explorer.exe  0x4320000   0x432ffff   VadS    PAGE_EXECUTE_READWRITE     16             1              Disabled

0x4320000:      mov     r10d, 0x80
0x4320006:      movabs  rax, 0x7feff86a138
0x4320010:      jmp     qword ptr [rax]
0x4320013:      nop
0x4320014:      mov     r10d, 0x81
0x432001a:      movabs  rax, 0x7feff86a138
0x4320024:      jmp     qword ptr [rax]
```

#### Kernel Mechanics

In Windows memory management:
1. Every process maintains a balanced binary search tree of Virtual Address Descriptors (`_MMVAD` structures) referenced from `_EPROCESS.VadRoot`.
2. Each VAD node defines a contiguous range of virtual addresses, protection flags (such as `PAGE_READONLY`, `PAGE_EXECUTE_READWRITE`), and allocation types (`Commit`, `Reserve`).
3. Normal application code is mapped from executable files on disk (`_MMVAD_LONG.Subsection != NULL`).
4. Injected code, reflective DLL loaders, and shellcode typically allocate private virtual memory using `VirtualAlloc` with `PAGE_EXECUTE_READWRITE` (`0x40`) without a backing file on disk.

`windows.malware.malfind` iterates through the VAD tree of each process, flagging private, committed memory ranges marked executable. It prints a 64-byte hexdump and disassembles the initial instructions, surfacing trampolines, indirect jumps, and unmapped executable stubs.

## Practical Investigation Workflow

When starting a memory analysis case:

1. **Establish Baseline**: Run `windows.info` to determine the exact OS build, architecture, and kernel offsets.
2. **Survey Execution**: Run `windows.pstree` and `windows.psscan` side by side to identify rogue parentage or unlinked rootkit processes.
3. **Inspect Runtime Context**: Query `windows.cmdline` and `windows.envars` on suspicious PIDs to discover command parameters, remote targets, or configuration tokens.
4. **Trace Network Activity**: Use `windows.netscan` to tie listening or established sockets back to running processes.
5. **Carve Artifacts**: Extract referenced files with `windows.filescan` and `windows.dumpfiles`.
6. **Detect Injections**: Scan memory ranges with `windows.malware.malfind` to identify in-memory payloads that never touched disk.
