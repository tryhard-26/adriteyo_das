# Memory forensics with Volatility 3

Whenever we investigate a compromised machine or tackle a memory CTF challenge, disk forensics only tells part of the story. Attackers inject shellcode directly into running processes, stash passwords in environment variables, and hold open network connections that never touch the file system. Physical memory gives us the live ground truth of what the system was doing at the moment of capture.

In this post, we'll walk through how physical RAM dumps work, how Volatility 3 handles kernel data structures under the hood, and how we can use its core plugins to pull apart a Windows memory dump.

## Memory dumps and physical memory

When an operating system runs, it uses hardware paging to manage physical RAM. On 64-bit x86 systems, the CPU uses four-level paging (PML4) to translate 48-bit virtual addresses into physical page frames, usually in 4 KB chunks.

To take a memory dump, an acquisition tool reads physical RAM page by page through direct kernel access (like `\Device\PhysicalMemory`) or an acquisition driver, saving the raw stream to disk.

In practice, we usually run into a few common formats:

* Raw dumps (`.raw`, `.bin`, `.dd`): Flat, byte-for-byte images of physical memory. They have no container headers, which makes them very easy to work with.
* Windows crash dumps (`.dmp`): Created when Windows hits a bugcheck. They contain crash header metadata, register values, and memory pages.
* Hypervisor snapshots (`.vmem`, `.sav`): Generated by virtual machines like VMware or VirtualBox, holding the guest's physical RAM alongside virtual CPU states.
* LiME dumps (`.lime`): Created on Linux systems with the Linux Memory Extractor kernel module, containing range headers for physical memory blocks.

If we open a raw dump in a hex editor, we do not see partitions, directory trees, or files. We see raw bytes from whatever was in RAM:

```text
00000000  4D 5A 90 00 03 00 00 00 04 00 00 00 FF FF 00 00  MZ..............
00000010  B8 00 00 00 00 00 00 00 40 00 00 00 00 00 00 00  ........@.......
```

Here the first bytes `4D 5A` are an `MZ` DOS header from an executable mapped in memory. Interleaved throughout the rest of the image are kernel tables, process heaps, thread stacks, cached disk blocks, and network socket buffers.

## How Volatility 3 handles symbols

If you used Volatility 2 in the past, you probably remember having to pass static profile names like `--profile=Win7SP1x64`. Every time Microsoft pushed a kernel update, structure offsets shifted slightly, and older profiles would break.

Volatility 3 drops static profiles completely. Instead, it reads Intermediate Symbol Format (ISF) JSON tables generated straight from Microsoft PDB debug symbols.

The engine divides work into three parts:

1. Memory layers read raw bytes from the file and translate virtual addresses to physical offsets using the Directory Table Base (DTB) in control register `CR3`.
2. Symbol tables tell the engine the exact size and byte offset of each structure member, such as `_EPROCESS`, `_FILE_OBJECT`, or `_CMHIVE`, for that specific kernel build.
3. Plugins query these layers and symbol tables to parse and print out the artifacts we care about.

To grab Volatility 3:

```bash
git clone https://github.com/volatilityfoundation/volatility3.git
cd volatility3
pip install -r requirements.txt
python3 vol.py -h
```

To parse the dump without us giving it an OS profile, Volatility scans physical RAM looking for the Kernel Debugger Data Block (`_KDDEBUGGER_DATA64`) or the Kernel Processor Control Region (`_KPCR`).

The DTB value (which gets loaded into the `CR3` register) provides the physical base address of the page directory table for the `System` process. That allows Volatility to translate virtual memory pointers into physical file offsets. From `ntoskrnl.exe`, it reads the symbol filename (`ntkrnlmp.pdb`) and GUID, then pulls the exact matching symbol table from Microsoft's symbol servers.

In the Windows kernel, each running process is tracked by an `_EPROCESS` structure in non-paged pool memory. Inside `_EPROCESS`, the `ActiveProcessLinks` member is a circular doubly linked list (`LIST_ENTRY`) of forward (`Flink`) and backward (`Blink`) pointers rooted at `PsActiveProcessHead`.

`windows.pslist` walks this list from head to tail. But there is a catch: if rootkit malware modifies these pointers using Direct Kernel Object Manipulation (DKOM), it can unlink its own `_EPROCESS` node from the list. The unlinked process continues to run just fine because the Windows thread scheduler looks at `_KTHREAD` dispatcher queues, not `ActiveProcessLinks`. When investigating rootkits, we pair `pslist` with `windows.psscan`, which scans memory for `_EPROCESS` pool tag signatures rather than relying on the linked list.

## Finding rogue parentage with windows.pstree

Process lists can be overwhelming to read flat. The `windows.pstree` plugin organizes processes into a tree based on their parent process IDs.

```bash
vol -f MemoryDump_Lab6.raw windows.pstree
```

```text

. 264   4       smss.exe        0xfa8002971470  2       29      N/A     False   2019-08-19 14:40:07.000000 UTC  N/A
...
. 480   384     services.exe    0xfa8002b99200  9       194     0       False   2019-08-19 14:40:11.000000 UTC  N/A

.. 724  480     svchost.exe     0xfa8002d4bb30  6       257     0       False   2019-08-19 14:40:11.000000 UTC  N/A
. 1944  1844    explorer.exe    0xfa800319a060  35      894     1       False   2019-08-19 14:40:19.000000 UTC  N/A
.. 880  1944    cmd.exe 0xfa8002324b30  1       21      1       False   2019-08-19 14:40:26.000000 UTC  N/A
.. 2124 1944    chrome.exe      0xfa800234eb30  27      662     1       False   2019-08-19 14:40:46.000000 UTC  N/A
... 2132 2124   chrome.exe      0xfa800234f780  9       75      1       False   2019-08-19 14:40:46.000000 UTC  N/A
.. 3716 1944    WinRAR.exe      0xfa80035e71e0  7       201     1       False   2019-08-19 14:41:43.000000 UTC  N/A
.. 4084 1944    DumpIt.exe      0xfa800156e400  5       46      1       True    2019-08-19 14:41:55.000000 UTC  N/A
```

Every `_EPROCESS` stores its own ID in `UniqueProcessId` and its parent ID in `InheritedFromUniqueProcessId`. The plugin maps these pairs into an indented hierarchy.

This lets us spot suspicious relationships quickly. For instance, `svchost.exe` instances should always spawn under `services.exe`. If we see `svchost.exe` running as a child of `cmd.exe` or `explorer.exe`, something is masquerading as a system service. In our dump, user programs (`chrome.exe`, `WinRAR.exe`, `DumpIt.exe`) originate cleanly under `explorer.exe` (PID 1944).

## Reading execution arguments with windows.cmdline

The `ImageFileName` field in `_EPROCESS` is capped at 15 characters and strips out launch arguments. To see what a process was actually told to do, we turn to `windows.cmdline`.

```bash
vol -f MemoryDump_Lab6.raw windows.cmdline
```

```text
PID     Process         Args

880     cmd.exe         "C:\Windows\system32\cmd.exe"
2124    chrome.exe      "C:\Program Files (x86)\Google\Chrome\Application\chrome.exe"
3716    WinRAR.exe      "C:\Program Files\WinRAR\WinRAR.exe" "C:\Users\Jaffa\Desktop\pr0t3ct3d\flag.rar"
4084    DumpIt.exe      "C:\Users\Jaffa\Downloads\DumpIt.exe"
```

To find these arguments, Volatility follows `_EPROCESS.Peb` into user-space memory to locate the Process Environment Block (PEB). Inside the PEB, `ProcessParameters` points to `_RTL_USER_PROCESS_PARAMETERS`, which stores `CommandLine` as a `UNICODE_STRING`. This immediately reveals what WinRAR was opening: `"C:\Users\Jaffa\Desktop\pr0t3ct3d\flag.rar"`.

## Finding files with windows.filescan

The `windows.filescan` plugin scans physical pages for pool allocations that match the `_FILE_OBJECT` structure.

```bash
vol -f MemoryDump_Lab6.raw windows.filescan
```

```text
Offset          Name

0x3e1ceeb0      \Windows\System32\samlib.dll
0x5ce6fb10      \Windows\System32\dui70.dll
0x5d9856d0      \Users\Jaffa\AppData\Local\Google\Chrome\User Data\Default\History
0x5fcfc4b0      \Users\Jaffa\Desktop\flag.rar
0x5fec1b40      \Users\Jaffa\AppData\Local\Microsoft\Windows\Explorer\thumbcache_256.db
```

Whenever a process opens a file, the Windows I/O manager creates a `_FILE_OBJECT` structure in pool memory. It contains pointers to the file path, device object, volume parameter block (`Vpb`), and cache control pointers (`SectionObjectPointer`). Because `filescan` searches for pool allocation tags rather than walking handle tables, it finds files even after the application has closed its handles, provided the memory hasn't been overwritten.

## Dumping files with windows.dumpfiles

Once we have the virtual address of a target `_FILE_OBJECT`, we can extract the file directly from memory using `windows.dumpfiles`.

```bash
vol -f MemoryDump_Lab6.raw -o ./extracted windows.dumpfiles --virtaddr 0x5fcfc4b0
```

Volatility follows `_FILE_OBJECT.SectionObjectPointer` to locate the `_CONTROL_AREA` and `_SEGMENT` structures used by the Windows cache manager. These structures map to the physical memory pages holding the cached file content. Volatility reads those pages and writes the reconstructed file to our output folder.

## Extracting credentials from windows.envars

The `windows.envars` plugin pulls environment variables for each process from user-mode memory.

```bash
vol -f MemoryDump_Lab6.raw windows.envars --pid 4084
```

```text
PID     Process          Offset      Variable Name           Value

4084    DumpIt.exe       0x4e1dc0    ProgramFiles(x86)       C:\Program Files (x86)
4084    DumpIt.exe       0x4e1dc0    ProgramW6432            C:\Program Files
4084    DumpIt.exe       0x4e1dc0    PSModulePath            C:\Windows\system32\WindowsPowerShell\v1.0\Modules\
4084    DumpIt.exe       0x4e1dc0    RAR password            easypeasyvirus
4084    DumpIt.exe       0x4e1dc0    TEMP                    C:\Users\Jaffa\AppData\Local\Temp
4084    DumpIt.exe       0x4e1dc0    USERNAME                Jaffa
4084    DumpIt.exe       0x4e1dc0    USERPROFILE             C:\Users\Jaffa
```

Environment blocks live at `_RTL_USER_PROCESS_PARAMETERS.Environment`. The block is formatted as a contiguous block of null-terminated UTF-16 strings (`KEY=VALUE`), ending with a double null. Because child processes inherit their parent's environment block by default, credentials or passwords set in parent command sessions often leak down the tree. Here, we see `RAR password=easypeasyvirus` sitting right in the environment table.

The `windows.registry.hivelist` plugin finds registry hives mapped into kernel memory.

## Spotting injected code with windows.malware.malfind

The `windows.malware.malfind` plugin scans for memory areas that look like injected code or unpacked payloads.

```bash
vol -f MemoryDump_Lab6.raw windows.malware.malfind
```

```text
PID     Process       Start VPN   End VPN     Tag     Protection               CommitCharge    PrivateMemory  File output

1944    explorer.exe  0x4320000   0x432ffff   VadS    PAGE_EXECUTE_READWRITE     16             1              Disabled

0x4320000:      mov     r10d, 0x80
0x4320006:      movabs  rax, 0x7feff86a138
0x4320010:      jmp     qword ptr [rax]
0x4320013:      nop
0x4320014:      mov     r10d, 0x81
0x432001a:      movabs  rax, 0x7feff86a138
0x4320024:      jmp     qword ptr [rax]
```

Each process tracks its allocated address space using a self-balancing binary tree of Virtual Address Descriptors (`_MMVAD`), rooted at `_EPROCESS.VadRoot`. Legitimate code normally maps from a file on disk, which sets the file subsection pointer. Injected code and reflective DLL loaders typically allocate private memory with `PAGE_EXECUTE_READWRITE` permissions via `VirtualAlloc`.

`windows.malware.malfind` flags committed, private memory pages that have execute permissions without backing files on disk. It disassembles the first few instructions at the base address, exposing shellcode stubs, jumps, and unmapped PE headers.
